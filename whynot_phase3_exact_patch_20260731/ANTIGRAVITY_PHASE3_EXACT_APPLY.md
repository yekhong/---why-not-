# WhyNot 3차 구현 코드 적용 요청서

이 문서는 Antigravity IDE의 AI에게 그대로 전달하는 적용 지시서입니다.

## 가장 중요한 지시

첨부된 파일은 이미 구현과 TypeScript 컴파일을 마친 코드입니다. 새로운 방식으로 다시 설계하지 말고 **첨부 파일을 정확히 적용**하세요.

- 기존 화면의 색상, 여백, 카드, 헤더, 타이포그래피를 재디자인하지 마세요.
- 기존 기능을 삭제하거나 이름을 바꾸지 마세요.
- 테스트용 기본 방 데이터와 테스트용 ID를 삭제하지 마세요.
- `.env`, API 키, 비밀번호, 토큰을 출력하거나 수정하지 마세요.
- GitHub commit/push, Vercel 배포, 원격 Supabase SQL 실행은 하지 마세요.
- 사용자의 승인 없이 코드를 임의로 단순화하거나 다른 라이브러리로 교체하지 마세요.

## 1. 적용할 파일

첨부된 3차 패키지에서 다음 파일을 프로젝트의 같은 경로에 복사하세요.

| 첨부 파일 | 프로젝트 적용 위치 | 처리 |
|---|---|---|
| `server.ts` | 프로젝트 루트의 `server.ts` | 기존 파일 교체 |
| `src/App.tsx` | `src/App.tsx` | 기존 파일 교체 |
| `src/types.ts` | `src/types.ts` | 기존 파일 교체 |
| `supabase_migration_phase3_decision_engine_forward.sql` | 프로젝트 루트 | 새 파일 추가만 하고 실행 금지 |
| `supabase_migration_phase3_decision_engine_rollback.sql` | 프로젝트 루트 | 새 파일 추가만 하고 실행 금지 |

이 파일들은 1·2차 구현을 포함한 현재 기준 파일입니다. 일부 코드 조각만 골라 붙이지 말고 파일 단위로 적용하세요.

## 2. 이번 3차에서 구현된 기능

### 2.1 빠른 결정 모드

빠른 결정은 일반 공개 투표가 아닙니다.

1. 참여자가 먼저 선택지를 작성합니다.
2. 전원이 작성 완료하기 전에는 다른 사람의 선택지를 볼 수 없습니다.
3. 작성이 끝나면 익명 선택지가 동시에 공개됩니다.
4. 다른 사람의 투표 결과를 보지 않고 각자 최종 투표합니다.
5. 전원의 투표가 끝난 뒤 결과를 동시에 공개합니다.

복잡한 평가 기준 합의만 생략하며, WhyNot의 익명성·동시 공개 원칙은 그대로 유지합니다.

### 2.2 최종 투표의 서버 확정

- 투표자는 클라이언트의 `userId`가 아니라 인증 쿠키의 사용자로 판단합니다.
- 투표 시작 시 참여자 명단을 고정합니다.
- 한 사람은 한 회차에 한 번만 제출할 수 있습니다.
- 선정해야 할 개수만큼 정확히 선택해야 합니다.
- 일부 참여자만 투표한 중간 집계는 응답하지 않습니다.
- 모든 투표가 끝난 뒤 서버가 결과를 확정합니다.
- 방장이 임의로 우승자를 보내는 이전 `/final-vote` 경로는 제거되었습니다.
- 방장이 임의로 방을 종료하는 이전 `/close` 경로는 제거되었습니다.

### 2.3 동률 처리

- 선정 경계에서만 동률을 계산합니다.
- 동률이 아니면 점수순으로 바로 확정합니다.
- 동률이면 `TIE_PENDING` 상태로 보존합니다.
- 방장은 특정 후보를 지정할 수 없습니다.
- 서버가 `crypto.randomInt()`를 사용해 필요한 자리 수만 추첨합니다.
- 실제 추첨은 한 번만 가능하며, 확정 뒤 다시 돌릴 수 없습니다.
- 미리보기 룰렛은 실제 결과에 영향을 주지 않습니다.

### 2.4 재검토 회차와 이력

- 결과를 재검토해도 이전 평가·투표·리포트를 덮어쓰지 않습니다.
- 새 `evaluation_rounds` 레코드를 만들고 후보는 `round_candidates`로 연결합니다.
- 구조화 모드는 합의된 기준으로 다시 평가합니다.
- 빠른 결정 모드는 새 익명 최종 투표를 시작합니다.
- 이전 회차는 결과 화면의 이력으로 남습니다.

### 2.5 근거 리포트

AI는 우승자를 선택하지 않습니다. 이미 확정된 결과와 팀의 평가를 다음 항목으로 정리합니다.

- 선정 이유
- 주요 우려
- 아직 확인되지 않은 가정
- 다음 검증 과제

생성된 문장과 입력·결과 스냅샷, 모델명, 프롬프트 버전을 `ai_reports`에 저장하도록 구현했습니다.

### 2.6 기준 합의 보완

- 방장의 단독 기준 확정 API를 제거했습니다.
- 참여 대상의 80%가 동의하면 평가 단계로 이동합니다.
- 전원이 투표했지만 80%에 미달하면 서비스가 멈추지 않습니다.
- 기존 기준 세트와 표는 보존하고 `criteria_set_version`을 증가시켜 새 보완 회차를 시작합니다.
- 이전 완료 표시와 동의 표가 새 버전에 섞이지 않습니다.

### 2.7 기존 결과 보호

- 새 방은 `engine_version = 3`을 사용합니다.
- 기존 완료 방은 과거 점수와 결과를 재계산하지 않습니다.
- DB 행에 새 컬럼이 없던 기존 완료 방은 화면 호환을 위해 `FINALIZED`로 해석합니다.

## 3. 보안상 반드시 유지할 코드

다음 코드를 삭제하거나 완화하지 마세요.

- 모든 방 API 앞의 인증·멤버십·방장 권한 미들웨어
- 요청 본문의 `userId`, `hostId`, `evaluatorId`를 인증 사용자의 ID로 강제하는 처리
- `seed-*` API를 운영 경로에서 404로 차단하는 처리
- `/final-vote`, `/close`, 직접 `/join` 경로 차단
- 평가 시 모든 활성 후보와 모든 확정 기준을 서버에서 검증하는 처리
- 투표 시작 시점 참여자 스냅샷
- 최종 투표 중간 집계 비공개 처리
- 작성자 ID·닉네임을 최종 확정 전 숨기는 응답 필터

테스트용 데이터가 코드에 남아 있는 것과 운영 사용자가 테스트 API를 실행할 수 있는 것은 다른 문제입니다. **테스트 데이터는 유지하고 테스트 API만 운영에서 차단**한 현재 구현을 그대로 유지하세요.

## 4. DB 파일 처리

이번 단계에서는 SQL을 실행하지 마세요.

마이그레이션 순서는 다음과 같습니다.

1. `supabase_migration_p0_bff_forward.sql`
2. `supabase_migration_phase2_persona_forward.sql`
3. `supabase_migration_phase3_decision_engine_forward.sql`

3차 SQL은 다음을 추가합니다.

- `rooms.decision_mode`
- `rooms.final_vote_status`
- `rooms.tie_candidate_idea_ids`
- `rooms.tie_slots`
- `rooms.current_round_id`
- `rooms.criteria_set_version`
- `evaluation_rounds`
- `round_candidates`
- `decision_votes`
- `evaluations.round_id`
- `ai_reports`

새 테이블은 브라우저가 직접 접근하지 못하도록 RLS를 켜고 `anon`, `authenticated` 권한을 회수합니다. 인증된 BFF 서버만 서비스 역할로 접근하는 구조입니다.

## 5. 로컬 확인 명령

파일 적용 후 다음 명령만 실행하세요.

```bash
npm run lint
npm run build:server
```

현재 제공 파일의 확인 결과는 둘 다 성공했습니다.

다음 경고는 오류가 아닙니다.

```text
Some chunks are larger than 500 kB after minification
```
